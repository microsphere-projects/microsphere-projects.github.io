Architecture ​

This page consolidates the capabilities of all 32 sub-projects into a single picture. The whole architecture follows one rule: each layer depends only on the layers below it, while cross-cutting capabilities plug into every layer.

Dependency flow ​

Dependencies point strictly downward — no layer ever depends on a layer above it:

L4 Cross-cutting   observability · i18n · security · dynamic · multiactive · configuration
                        ↓ weave in (pluggable, no compile-time dependency)
L3 Integration     gateway · nacos · redis · mybatis · hibernate · druid
                   sentinel · resilience4j · netflix · dubbo · tomcat · etcd
                        ↓ depends on
L2 Framework       microsphere-spring · microsphere-spring-boot · microsphere-spring-cloud
                        ↓ depends on
L1 Runtime         microsphere-java · logging · java-enterprise · jakarta · microprofile
                        ↓ depends on
L0 Foundation      microsphere-build (parent POM) · microsphere-bom (version governance)

This chain delivers three concrete benefits:

  1. Trimmable — using microsphere-java alone pulls in no Spring dependency whatsoever.
  2. Consistent versions — every layer shares L0's build baseline and version governance, so repositories never drift.
  3. Non-intrusive cross-cutting capabilities — L4 weaves in through interception pipelines and events, so observability and resilience arrive without touching business code.

Layer responsibilities ​

LayerResponsibilityKey constraint
L0 FoundationMaven parent POM, plugin versions, profiles and BOM governanceCovers five Java TLS versions: 8 / 11 / 17 / 21 / 25
L1 RuntimeFramework-free Java capabilities: utilities, reflection, type conversion, events, logging abstractionMust not depend on Spring or any application framework
L2 FrameworkEnhancements for Spring, Spring Boot and Spring CloudMust stay a drop-in additive enhancement that never changes default behaviour
L3 IntegrationAdapters for concrete infrastructure: registries, data access, caching, RPC, resilienceHooks in via interception and extension points, never touching business code
L4 Cross-cuttingObservability, i18n, security, dynamic configuration, multi-active routingWoven in via SPI and events, individually switchable

Choosing your starting point ​

Start small

Don't pull in everything at once. The recommended path is:

  1. Start with microsphere-java-dependencies and use the utility library;
  2. Add microsphere-spring-dependencies once you have a Spring app to fix configuration and startup problems;
  3. Move to microsphere-spring-cloud-dependencies when you go distributed;
  4. Finally adopt L3 / L4 by pain point — observability, flow control and i18n as needed.

Don't mix release lines

main (0.2.x) and 1.x (0.1.x) target different Spring generations. Never mix modules from both lines in one application. See the compatibility matrix.
